# `data/synthetic/synthea/`: Synthea charts for chart-scan input

> **Everything here is simulated: "Synthea synthetic EHR (simulated)".** These are synthetic
> patients generated by [Synthea](https://github.com/synthetichealth/synthea) (the Regeneron
> judges' recommendation; the starter sheet names it as the source of "synthetic notes and
> medication lists" for chart-scan input). No real person, record or identifier is in this
> directory. Every vital sign here is a Synthea value: `is_measured: false`.

## What is in this directory

| File | What it is | Written by |
|---|---|---|
| `participants.json` | 12 NSCLC patients relabelled `P-001` … `P-012`: sex, age at the reference date, NSCLC diagnosis date + TNM stage + SNOMED codes, clinically relevant comorbidities, allergies, active medications (RxNorm, parsed ingredient, start date, and what Interim's con-med matcher proposes), cancer therapy administrations, encounters in the last 12 months, baseline vitals, smoking status, counts | `scripts/synthea/import_synthea.py` |
| `notes.json` | 72 de-identified clinical notes (6 per participant, last 12 months, every emergency-encounter note included) with a **ground-truth** block per note | same |
| `manifest.json` | sha256 + bytes of every output and input table, the generator config excerpt (jar sha256, seeds, flags), per-bundle input hashes, summary stats | same |
| `condition_filter.json` | which SNOMED conditions count as medical history (table, with `source`/`rationale`) | hand-written |
| `import_tables.json` | every code list, window and word list the importer uses: NSCLC codes → stage, encounter classes, vitals LOINC codes, smoking codes, the ingredient heuristic, the 12-month window and the 6-notes cap | hand-written |
| `README.md` | this file | hand-written |

Total ≈ 465 KB (budget 1.5 MB, enforced by a test).

## How it was generated

`scripts/synthea/synthea_config.json` pins everything. The committed data came from:

- **Synthea** `master-branch-latest` release asset `synthea-with-dependencies.jar`, version `d9d07a6`,
  197,025,542 bytes, sha256 `018ad7f04f7aacb995804d7d4781c76d5fc714f7f23257ba50daa9eefae224ac`,
  retrieved 2026-10-10T21:47:58Z. Run in Docker `eclipse-temurin:17-jre` (no local Java needed).
- **Population:** `-p 12 -a 50-80 -s 20261010 -cs 20261010 -r 20261010 Massachusetts`, FHIR R4 +
  CSV + clinical-note exporters, `exporter.years_of_history=3`, `generate.only_alive_patients=true`,
  `generate.max_attempts_to_keep_patient=5000`.
- **Keep module** `scripts/synthea/keep_nsclc.json`: keeps only people with an *active*
  non-small cell lung cancer diagnosis (SNOMED 254637007 and TNM stage 1–4 concepts), the
  population of the demo study (EMPOWER-Lung 1, NCT03088540).
- **Two runs.** NSCLC is rare, so the keep module rejects most simulated people. The primary run
  kept 11 of 12 in 896 s before Synthea gave up on the 12th; a top-up run with the next seed
  (`-p 1 -s 20261011 -cs 20261011`, CSV export off) added one patient in 45 s. Both are recorded
  in `manifest.json` → `runs`.

### Regenerate

```bash
# Show the exact commands (downloads nothing, runs nothing)
.venv/Scripts/python.exe scripts/synthea/run_synthea.py --dry-run

# Download + verify the pinned jar (cached outside the repo in %LOCALAPPDATA%/interim/synthea
# or ~/.cache/interim/synthea), generate (~10-15 min), top up if short, then import here
.venv/Scripts/python.exe scripts/synthea/run_synthea.py --out C:/tmp/synthea-out

# Import only, from an existing Synthea output directory (repeat --in for a top-up run)
.venv/Scripts/python.exe scripts/synthea/import_synthea.py --in <out> --in <out_topup>

# Determinism: re-import into a temp dir and require byte-identical files. The raw output
# has no default location: pass --in, or set INTERIM_SYNTHEA_OUT (os.pathsep-separated,
# primary run first; ';' on Windows, ':' elsewhere)
INTERIM_SYNTHEA_OUT='<out>;<out_topup>' .venv/Scripts/python.exe scripts/synthea/import_synthea.py --check
```

`run_synthea.py` uses a local `java` (11+) if one is on `PATH`, else Docker; it sets
`MSYS_NO_PATHCONV=1` so Git Bash on Windows does not rewrite the `docker -v` paths.
`master-branch-latest` is a moving tag: if the downloaded jar's sha256 differs from the pin the
script stops; `--accept-new-jar` records the new hash in the config and continues (the
regenerated data will then differ from the committed data; review the diff).

A full `--check` needs the raw Synthea output on disk (via `--in` or `INTERIM_SYNTHEA_OUT`).
Without it (a clean clone, CI) it verifies only the manifest, and prints a warning that
importer drift is **not** verified; add `--strict` to make that case fail. The import also
depends on `packages/rules/data/medlist.json` (the con-med matcher's list), because
`participants.json` embeds the matcher's proposals (`interim_match`). The manifest records that
list's sha256 (`matcher_medlist_sha256`), and `--check` compares it with the current file in
both modes, so a medlist change fails the check even in CI. When the change is intended,
re-import from the raw output (regenerate it with `run_synthea.py` if needed) and commit.

### Why the raw FHIR is not committed

The 12 FHIR bundles are ≈ 66 MB (plus ≈ 26 MB of CSV), mostly claims, explanation-of-benefit
and lab resources the demo never reads, and they carry Synthea's realistic-looking names,
addresses, phone numbers, SSNs and UUIDs. The committed files keep only what Interim uses,
de-identified, and the pipeline above regenerates the source from pinned inputs.

## De-identification rules

Synthea's people are fictional, but their records look real (names such as `Jane123 Doe45`,
invented here for illustration, a street
address, `555-` phone numbers, `999-` SSNs, MRNs, driver's licence and passport numbers). So:

1. **No names.** In note text, every token of the patient's given and family names (with and
   without Synthea's numeric suffix) becomes the participant label (`P-003 is a 70 year-old …`);
   an honorific before it and repeated labels collapse. Any other Synthea-style name token
   (`Word123`) becomes `[name]`. Practitioner and organization names are never copied.
2. **No addresses, phone numbers or identifiers.** Address lines, city, postal code, telecom
   values and every `Patient.identifier` value (Synthea id, MRN, SSN, licence, passport) are
   replaced by `[redacted]` if they occur in text, and never copied into fields. (In the
   committed run neither placeholder was needed: Synthea's notes contain only the given name.)
3. **No Synthea UUIDs.** `synthea_ref` is the first 12 hex characters of sha256(Synthea UUID),
   enough to trace a participant back to a regenerated bundle, not reversible. Bundle file
   names (which contain names) are never written; inputs are listed by label and bundle sha256.
4. **No birth dates.** Only `age_at_reference` (age on 2026-10-10).
5. **Social-determinant "conditions"** (employment, education, criminal record, intimate
   partner abuse, refugee status) are excluded from `comorbidities` and from the per-note
   diagnosis ground truth by `condition_filter.json`. They remain inside Synthea's note text
   ("Patient has a history of … stress (finding)"), which is reproduced as generated.

`scripts/tests/test_synthea_import.py` enforces this: it builds the list of every name token,
address, phone number, identifier and UUID from the source Patient resources (when the raw
output is on disk) and asserts none appears in any output, in this README, in
`docs/eval/synthea_results.md`, or in the pipeline's scripts, tables and tests. In CI it runs the
same checks on a hand-built FHIR bundle and pattern checks (UUIDs, `Word123`, `555-…`, `999-…`)
on the committed files and on this README and the results doc. Examples in prose and code
comments use invented names.

## The ground truth in `notes.json`

The point of these notes is to score Interim's deterministic chart scanner
(`interim_rules.chartscan`) against something it did not produce. So the answer key comes from
the **structured FHIR record** wherever it exists, and every block says where it came from
(`ground_truth.sources`):

| Field | Source |
|---|---|
| `active_medications_at_note` | Structured: every MedicationRequest active on the note date (see "Medication intervals"), **plus** the note's own `# Medications` list. Each item has `sources`: `["structured"]`, `["note_section"]` or both. |
| `prescribed_at_encounter` | FHIR `MedicationRequest.encounter` = the note's encounter (with `n_orders`) |
| `conditions_diagnosed_at_encounter` | FHIR `Condition.encounter` = the note's encounter, filtered by `condition_filter.json` (`n_conditions_excluded_by_filter` counts the rest) |
| `is_emergency_encounter` | FHIR `Encounter.class == EMER` |
| `chief_complaints` | The note's `# Chief Complaint` bullets. Synthea has no structured chief-complaint resource; this is the documented fallback. |

**Synthea's note text and its structured record disagree, and that is useful.** Across the 72
notes, counting one item per `active_medications_at_note` entry (one per RxNorm code or note-list
line), 109 medication items are in both, 171 are only in the structured record (e.g. a
participant on clopidogrel, metoprolol, nitroglycerin and simvastatin whose emergency note says
"No Active Medications.") and 189 are only in the note's list (Synthea keeps listing one-off
injections such as docetaxel long after they were given). A text-only scanner can find at most
the `note_section` items; score its *recall* against those, and report the `structured`-only
items as what chart text alone misses. `docs/eval/synthea_results.md` counts per **leading
ingredient** per note instead, because a scanner names ingredients, not products. The
difference is six items: on 6 of P-002's notes a structured-only `Simvastatin 20 MG` is active
alongside the listed `Simvastatin 10 MG`, and per ingredient it merges into that item, which is
already counted as in both. So the eval reports 165 structured-only items rather than 171; the
other two counts are the same in both units.

**Chief complaints are the person's standing symptom list**, repeated on every note (Synthea
renders the simulated person's current symptoms, not a visit-specific complaint): Cough 54,
Chest Pain 42, Fatigue 18, Frequent Urination / Hunger / Thirst 12 each, Cramping 6, Tingling 6,
"urinary frequency" 6.

### Medication intervals

FHIR R4 MedicationRequests from Synthea have no end date. When the run exported CSV, the
importer uses Synthea's own `medications.csv` STOP column (same simulation, structured):
`medication_interval_source: "synthea_csv"` (11 participants). The top-up run had no CSV, so
P-007 uses `"fhir_status_heuristic"`: `active` → open-ended; a completed community prescription
lasts until the next prescription of the same RxNorm code (Synthea renews chronic drugs yearly),
otherwise one day; completed inpatient orders last their own day. Validation: on the 66 selected
notes of the CSV participants, the heuristic gives the same active RxNorm set as the CSV on 64
(97%).

### Ingredients and the con-med matcher

`ingredient` is the leading ingredient parsed from the RxNorm display by the heuristic in
`import_tables.json` (`"24 HR metoprolol succinate 100 MG Extended Release Oral Tablet"` →
`metoprolol`; `"1 ML DOCEtaxel 20 MG/ML Injection"` → `docetaxel`; combinations such as
`"Acetaminophen 325 MG / Oxycodone Hydrochloride 5 MG Oral Tablet"` → leading `acetaminophen`
with `ingredients: ["acetaminophen", "oxycodone"]`; `[Brand]` → `brand`). It is a string
heuristic, not an RxNorm lookup.

`interim_match` is Interim's deterministic con-med matcher (`interim_rules.conmed.match_conmed`,
bundled list, NOT RxNorm) run on the full display. On the 36 active medications it proposes the
right ingredient for **24 (66.7%)**, a wrong drug for 2 and nothing for 10:

- unmatched because the drug is not in `packages/rules/data/medlist.json`: clopidogrel (5
  participants), fentanyl, alendronic acid, alteplase, insulin (2);
- wrong: `Vitamin B12 5 MG/ML Injectable Solution` → methylphenidate at 0.71, because the token
  "Vitamin" is 2 edits from the brand "ritalin". A real false positive of the Levenshtein ≤ 2
  rule, the kind `docs/WHAT_IT_GETS_WRONG.md` §4 describes.

These are Synthea's long RxNorm strings, not what a participant types at the kiosk, so the
number is a stress test of the list's coverage, not the kiosk's accuracy.

## Limitations (also candidates for `docs/WHAT_IT_GETS_WRONG.md`)

- **Every participant is stage 1.** Synthea's lung-cancer module plus "alive at the reference
  date" selects early-stage survivors; the demo study enrolled advanced/metastatic NSCLC.
- **No immunotherapy.** Synthea treats NSCLC with cisplatin + paclitaxel; it has no cemiplimab
  (Libtayo) or other PD-1 inhibitor, so these charts show chemotherapy-era adverse-event context,
  not immune-related AEs.
- **Notes are templated.** Same sections every time; chief complaints repeat; no free-text
  narrative, negations, or "patient reports …" sentences. They exercise the scanner's symptom
  and medication lexicons and its **historical** logic (Synthea's long "Patient has a history
  of …" lists), but not its negation logic. `docs/eval/synthea_results.md` shows both sides of
  the history window: 17 history-list mentions correctly excluded, and 8 false positives where
  the term sits 15 to 22 words after the cue, beyond the scanner's 8-word window.
- **No allergies** were generated for this cohort (`allergies: []` everywhere; notes say "No Known
  Allergies.").
- Labels `P-001` … `P-012` are assigned in Interim's participant label space (sorted by birth
  date, then Synthea id). Whether a Synthea chart is attached to the seeded kiosk participant
  with the same label is a seed/API decision; the seeded participants have no demographics, so
  nothing here contradicts them.
